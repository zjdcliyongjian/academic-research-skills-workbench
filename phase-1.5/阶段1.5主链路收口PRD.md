# AI 科研副导师工作台｜阶段 1.5 主链路收口 PRD

> 文档状态：待确认  
> 版本：V1.0  
> 日期：2026-09-15  
> 产品阶段：阶段 1 MVP 之后、阶段 2A 可信文献调研之前

## 1. 本阶段结论

阶段 1 已经完成课题创建、独立 Vault、资料登记、Codex 连接、Skill 路由、Idea 评估、运行留痕和 Markdown/Word 导出。

阶段 1.5 不继续扩展新的科研能力，优先把现有主链路收口为一套可信、可恢复、可审查的状态机：

`运行 Skill → 保存草稿 → 人工审阅 → 采用 / 驳回 / 要求修改 → 形成正式版本 → 推进阶段 → 正式导出`

完成后，工作台应能明确回答以下问题：

1. 当前运行到了哪一步？
2. 哪个结果只是 AI 草稿？
3. 哪个版本已经被人确认采用？
4. 为什么能够进入下一研究阶段？
5. 正式导出的内容来自哪个采用版本？
6. 运行失败、中断或重启后如何继续？

## 2. 当前问题

### 2.1 当前已实现能力

- Idea Evaluator 运行结束后可保存草稿并人工采用。
- 运行、审批、版本和 Codex 任务绑定均有本地记录。
- 深度文献调研和论文蓝图可以发起 Skill 运行并展示输出。
- Markdown 和 Word 文件可以生成、预览与下载。

### 2.2 必须收口的问题

1. 只有 Idea 评估结果具有完整的“采用此版本”入口。
2. 文献调研和论文蓝图运行结束后无法形成独立的正式版本。
3. 当前采用接口只处理 Idea 评估，并固定把项目推进到文献调研阶段。
4. 正式导出可能使用“已完成但未人工采用”的运行结果。
5. 缺少“驳回”和“要求修改”两类内容审阅决定。
6. 缺少清晰的运行取消、失败重试、连接异常和恢复入口。
7. 项目台只显示数量，不能清楚显示各阶段的草稿、正式版本和人工待办。
8. 尚未建立覆盖 Idea、调研、蓝图、导出的完整状态机测试。

## 3. 产品目标

### 3.1 核心目标

- 所有已接入阶段统一使用相同的草稿与人工确认机制。
- 正式成果与 AI 草稿在数据、界面和导出层面完全分开。
- 阶段推进必须由有效的人工采用决定触发。
- 任何正式导出都能追溯到具体运行、正式版本和采用时间。
- 常见失败可以在工作台内识别、恢复或重新运行。

### 3.2 成功标准

- 用户不进入文件夹也能看懂项目当前状态和下一步。
- 用户能够比较同一阶段的多个草稿，并选择其中一个采用。
- 未采用或被驳回的内容不会混入正式成果。
- 服务重启后，运行、审阅决定、正式版本和当前阶段保持一致。
- 端到端测试覆盖三个研究阶段和两种导出格式。

## 4. 本阶段范围

### 4.1 包含范围

1. 通用运行结果审阅机制。
2. 通用正式版本机制。
3. 研究阶段状态机。
4. 草稿、采用、驳回和修改后的版本关系。
5. 正式导出边界。
6. 运行失败、取消、重试和恢复界面。
7. 项目台状态与人工待办展示。
8. 数据迁移、事件留痕和自动化验收。

### 4.2 不包含范围

- 网页自动抓取、正文抽取和元数据识别。
- PDF 内容解析、DOI 核验和 BibTeX 生成。
- 章节级论文写作。
- 图表生成、投稿前审查和审稿回应工作流。
- PDF、LaTeX 和期刊模板导出。
- 多用户、云端部署、账号权限和协同编辑。

以上能力分别进入阶段 2A、2B、2C 和 2D。

## 5. 用户角色与原则

### 5.1 用户角色

阶段 1.5 只支持单机单用户：研究者本人既是任务发起人，也是正式版本的最终确认人。

### 5.2 核心原则

- Skill 提供专业工作方法，但不能代替用户作出采用决定。
- 运行完成不等于结果已采用。
- 采用结果不等于来源事实已被核验。
- 驳回不删除历史记录。
- 修改不覆盖原草稿，而是形成关联的新运行或新版本。
- 正式导出只使用当前有效的正式版本。

## 6. 统一研究阶段

| 阶段代码 | 界面名称 | 对应主要 Skill | 进入条件 | 完成条件 |
|---|---|---|---|---|
| `brief` | 课题建立 | `vibe-research-workflow` | 创建课题 | 已建立课题和证据目录 |
| `idea` | Idea 评估 | `idea-evaluator` | 已有课题卡 | 至少一个 Idea 正式版本被采用 |
| `research` | 文献调研 | `deep-research` | Idea 已采用 | 至少一个调研正式版本被采用 |
| `blueprint` | 论文蓝图 | `tech-paper-template` 或 `benchmark-paper-template` | 调研已采用 | 至少一个蓝图正式版本被采用 |
| `export` | 正式导出 | 导出服务 | 蓝图已采用 | 至少生成一个正式导出文件 |

补充规则：

- 上传资料不会自动跳过 Idea 评估。
- 运行 Skill 不推进阶段；只有采用该阶段结果后才推进。
- 用户可以返回已经完成的阶段重新运行，但不会自动让后续正式版本失效。
- 如果用户采用了上游的新版本，系统必须把下游正式版本标记为“需要复核”，由用户决定保留或重新生成。

## 7. 运行状态机

### 7.1 运行状态

| 状态 | 含义 | 用户可执行操作 |
|---|---|---|
| `queued` | 已创建，等待 Codex 接收 | 取消 |
| `running` | Codex 正在输出 | 查看实时输出、取消 |
| `waiting_approval` | 等待一次性工具审批 | 允许一次、拒绝、取消运行 |
| `completed` | 运行完成，结果仍为草稿 | 预览、采用、驳回、要求修改、重新运行 |
| `failed` | 运行失败 | 查看原因、重试 |
| `cancelled` | 用户主动取消 | 重新运行 |
| `declined` | 结果经内容审阅后被驳回 | 查看原因、基于反馈重新运行 |

### 7.2 运行终态

`completed`、`failed`、`cancelled` 和 `declined` 均为本次运行的终态。采用是对运行结果的审阅决定，不把运行状态改成另一个含义；采用信息单独记录。

## 8. 人工审阅机制

### 8.1 四种决定

#### 采用此版本

- 将当前草稿复制为该阶段新的正式版本。
- 记录采用人、采用时间、运行 ID、Skill、版本号和内容哈希。
- 把该版本设为该阶段“当前正式版本”。
- 满足阶段条件时推进到下一阶段。

#### 驳回此版本

- 必须填写驳回原因。
- 草稿和运行记录继续保留。
- 不形成正式版本，不推进阶段。

#### 要求修改

- 必须填写修改要求。
- 基于原运行创建新运行，记录 `parent_run_id`。
- 新运行继承原任务上下文，并附加用户反馈。
- 原草稿保持不变。

#### 暂不处理

- 不改变任何状态。
- 结果继续显示在“待人工审阅”中。

### 8.2 多版本规则

- 同一阶段可以存在多个草稿和多个历史正式版本。
- 同一阶段只能有一个“当前正式版本”。
- 采用新版本时，旧正式版本变为“已替代”，但不删除。
- 用户可查看版本之间的生成时间、Skill、运行 ID、采用记录和文本差异。
- 阶段 1.5 至少实现基本版本列表；逐行差异对比可作为增强项，但数据结构必须预留。

## 9. 正式文件目录规则

| 阶段 | 草稿目录 | 正式版本目录 | 审阅记录 |
|---|---|---|---|
| Idea 评估 | `04-idea/drafts` | `04-idea/versions` | `04-idea/reviews.jsonl` |
| 文献调研 | `05-research/drafts` | `05-research/versions` | `05-research/reviews.jsonl` |
| 论文蓝图 | `06-blueprint/drafts` | `06-blueprint/versions` | `06-blueprint/reviews.jsonl` |

统一命名建议：

`{stage}-{version}-{date}-{short-run-id}.md`

例如：

`research-v002-20260915-a18f4c2d.md`

每个正式文件使用 YAML 头记录：

```yaml
stage: research
version: 2
status: active
run_id: a18f4c2d-...
skill: deep-research
adopted_at: 2026-09-15T10:30:00+08:00
content_sha256: ...
supersedes: research-v001-...
```

## 10. 数据模型调整

### 10.1 `runs` 增补字段

- `parent_run_id`：修改或重试所依据的原运行。
- `cancel_requested_at`：用户发出取消请求的时间。
- `review_status`：`pending / adopted / rejected / revision_requested`。
- `reviewed_at`：审阅完成时间。
- `review_note`：驳回原因或修改要求。

### 10.2 新增 `stage_versions`

建议字段：

- `id`
- `project_id`
- `stage`
- `version_number`
- `run_id`
- `skill_name`
- `relative_path`
- `content_sha256`
- `status`：`active / superseded / needs_review`
- `adopted_at`
- `superseded_at`

### 10.3 新增或扩展事件记录

事件类型至少包含：

- `run.queued`
- `run.started`
- `run.waiting_approval`
- `run.completed`
- `run.failed`
- `run.cancel_requested`
- `run.cancelled`
- `review.adopted`
- `review.rejected`
- `review.revision_requested`
- `version.activated`
- `version.superseded`
- `version.needs_review`
- `stage.advanced`
- `export.created`

所有事件继续写入本地 SQLite，并在 Vault 的 `99-system` 中保留可脱离工作台读取的 JSONL 副本。

## 11. 接口需求

### 11.1 审阅接口

`POST /api/runs/{runId}/reviews`

请求示例：

```json
{
  "decision": "adopt",
  "note": "采用该版本作为当前文献调研结论"
}
```

`decision` 支持：

- `adopt`
- `reject`
- `request_revision`

### 11.2 重试与修改

- `POST /api/runs/{runId}/retry`
- `POST /api/runs/{runId}/revise`

修改请求必须携带用户反馈，并产生新的运行 ID。

### 11.3 取消

`POST /api/runs/{runId}/cancel`

若底层 Codex 已经完成，则返回最新真实状态，不能把已完成任务伪装为已取消。

### 11.4 正式版本

- `GET /api/projects/{projectId}/versions`
- `GET /api/projects/{projectId}/versions/{versionId}`
- `GET /api/projects/{projectId}/versions/{versionId}/content`

### 11.5 正式导出

`POST /api/projects/{projectId}/exports`

新增参数：

```json
{
  "format": "docx",
  "language": "zh",
  "mode": "formal"
}
```

- `formal`：只读取当前有效正式版本。
- `draft`：允许导出指定草稿，但标题、页眉和文件名必须标注“草稿”。

## 12. 界面需求

### 12.1 项目台

每个阶段显示：

- 当前状态：未开始、运行中、待审阅、已完成、需复核。
- 草稿数量。
- 当前正式版本号及采用时间。
- 待人工审批数与待内容审阅数。
- 明确的下一步按钮。

### 12.2 Skill 运行结果区

运行完成后固定提供：

- 预览草稿。
- 采用此版本。
- 驳回。
- 要求修改。
- 重新运行。
- 打开 Codex。

采用和驳回必须通过确认面板完成，避免误触。

### 12.3 版本列表

每个阶段右侧或下方增加“版本与审阅记录”：

- 版本号。
- 草稿或正式版本状态。
- Skill 名称。
- 生成时间和采用时间。
- 运行 ID。
- 审阅意见。
- 预览入口。

### 12.4 异常状态

失败卡片必须显示：

- 对用户可理解的失败摘要。
- 原始错误详情的折叠区域。
- 是否产生了部分草稿。
- 重试、重新连接 Codex、打开 Codex 三个可选动作。

不得只显示“失败，请重试”。

## 13. 导出规则

### 13.1 正式导出

- 必须至少存在一个正式采用版本。
- 默认依次读取 Idea、文献调研和论文蓝图的当前正式版本。
- 尚未完成的阶段明确标注“尚无正式版本”，不能使用未采用草稿自动补位。
- 导出文件记录所有使用版本的 ID、运行 ID、采用时间和内容哈希。

### 13.2 草稿导出

- 只有用户主动选择“导出草稿”时允许。
- 文件名带 `DRAFT` 或“草稿”。
- 文档首页和页眉显著标注“未经人工采用，不得作为正式研究成果”。
- 草稿导出不改变项目阶段。

### 13.3 中英文边界

- 阶段 1.5 继续提供中文和英文导出入口。
- 如果当前正式内容只有中文，英文导出应明确属于翻译输出，不能伪装成独立核验过的英文研究版本。
- 双语并排或期刊级英文润色不在本阶段范围。

## 14. 上游变更与下游复核

当用户采用新的上游正式版本时：

1. 系统检测是否存在下游正式版本。
2. 若存在，弹出影响提示。
3. 下游版本状态改为 `needs_review`，但不删除文件。
4. 正式导出时明确提示存在待复核版本。
5. 用户可以选择：继续沿用、重新运行下游阶段、暂不导出。

阶段依赖关系：

`Idea → 文献调研 → 论文蓝图 → 正式导出`

## 15. 数据迁移

现有项目必须无损迁移：

1. 已采用的 Idea 评估生成 `idea-v001` 正式版本记录。
2. 已完成但未采用的调研和蓝图运行统一标记为 `review_status=pending`。
3. 现有导出文件保留，不追溯修改；在文件库标记为“旧版导出”。
4. 迁移前备份 SQLite 数据库。
5. 迁移脚本支持重复执行，不产生重复版本。
6. 迁移失败时保持旧数据可读，不自动删除或覆盖。

## 16. 验收用例

### AC-01 Idea 多草稿采用

- 连续运行两次 Idea Evaluator。
- 两份草稿均可预览。
- 采用第二份后形成 `idea-v001`。
- 第一份继续保留为待审阅或被驳回草稿。
- 项目进入文献调研阶段。

### AC-02 文献调研正式版本

- 运行两次 Deep Research。
- 驳回第一份并填写原因。
- 采用第二份并形成 `research-v001`。
- 项目进入论文蓝图阶段。

### AC-03 要求修改

- 对一个已完成草稿填写修改意见。
- 系统创建新的关联运行。
- 新运行记录原运行 ID 和修改意见。
- 原草稿内容与文件保持不变。

### AC-04 蓝图类型

- 通用或技术论文调用 `tech-paper-template`。
- Benchmark 论文调用 `benchmark-paper-template`。
- 采用后形成 `blueprint-v001` 并进入正式导出阶段。

### AC-05 正式导出边界

- 存在未采用的最新草稿和较早的正式版本。
- 正式 Markdown/Word 只能使用正式版本。
- 导出文件中记录使用的版本信息。

### AC-06 草稿导出边界

- 用户主动选择导出草稿。
- 文件名和正文均带明显草稿标识。
- 项目阶段不发生变化。

### AC-07 上游版本变更

- 已存在调研和蓝图正式版本。
- 采用新的 Idea 版本。
- 调研和蓝图变为“需复核”。
- 系统不得静默把旧下游内容视为最新可靠成果。

### AC-08 取消与重试

- 取消排队中或运行中的任务。
- 运行状态与 Codex 实际结果一致。
- 失败或取消后可以创建新运行，旧记录仍可追溯。

### AC-09 服务重启恢复

- 在待审批、待审阅和已采用三种状态下分别重启服务。
- 页面重新加载后状态、版本、反馈和项目阶段保持一致。

### AC-10 端到端主链路

使用一个真实课题完成：

`创建课题 → 上传资料 → Idea 两次运行并采用 → 调研两次运行并采用 → 蓝图运行并采用 → 正式 Markdown/Word 导出 → 重启后复核`

全过程不得出现未采用内容进入正式导出的情况。

## 17. 自动化检查要求

- 数据库迁移测试。
- 通用采用、驳回和修改测试。
- 项目阶段推进测试。
- 上游变更导致下游复核测试。
- 正式导出不得回退到未采用运行的测试。
- 草稿导出水印和命名测试。
- 取消、失败和重试测试。
- Vault 文件与数据库记录一致性测试。
- TypeScript 类型检查、Vitest、生产构建全部通过。
- 使用真实 Word 打开或渲染最终 DOCX，检查分页、表格、字体、缺字和溢出。

## 19. 发布门槛

满足以下条件后，阶段 1.5 才能标记为完成：
